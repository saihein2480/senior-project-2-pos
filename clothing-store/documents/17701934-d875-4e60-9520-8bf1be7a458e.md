# Committee Review: Swe Trendy Hub (POS + Online Storefront)

**Overall verdict:** The feature set is broad and some parts are well engineered: stock reservation, the returns ledger and MMPay signature checks. The weak areas are **security, money correctness and workflow consistency**, which are the areas a committee will probe first. Most of the backend trusts the browser: it trusts prices, totals, user IDs and roles sent by the client. Order state is spread across 5+ fields with no state machine. Neither app has any automated tests.

Paths are relative to `pos-clothing-store/clothing-store` (POS) or `pos-clothing-store-web` (Web).

Not verified: which Firestore rules are actually deployed (the repo file is marked DRAFT), and whether production uses MMPay sandbox keys.

## 1. Critical: fix before the defense

| # | Problem | Evidence | Why it matters |
|---|---|---|---|
| C1 | **Most API routes have no authentication.** Only 2 of 25 POS routes check an ID token and role. | POS `api/staff/route.ts` (GET/POST/PUT/DELETE are all open; PUT passes the raw body into `updateStaff`, including `role`). The same applies to `settings`, `stocks`, `customers`, `expenses`, `shops`, `admin/fix-refund-status`, and the R2 `upload`/`delete` routes. | Anyone with the URL can list staff, change tax and exchange rates, edit prices, read customer PII, or delete product images. | C2 | **The customer decides the price.** | Web `api/mmpay/create-order/route.ts` sends `body.amountMmk` straight to MMPay. `create-cod/route.ts` uses `subtotalTHB`, `totalTHB` and per-line prices from the request. `mmpay/webhook` verifies the signature but never compares `payload.amount` to a server-computed total. | A modified request can buy anything for 1 MMK, and the system still records it as "completed" revenue and awards loyalty points. |
| C3 | **Database rules are an undeployed draft that conflicts with the code.** | `firestore.rules` L13 says "DRAFT". ## 2. Backend weaknesses

- **No order state machine.**
  - `approveTransaction` always sets `completed`, so it can bring a cancelled or refunded order back as revenue.
  - `rejectTransaction` sets `status` but not `orderStatus`.
  - `updateDeliveryStatus("delivered")` forces `completed` whatever the previous state.
  - `cancelPaidTransaction` has no guard: cancelling twice resets `cancellationRefund` to `pending`, which creates a second payout.
  - Location: POS `services/transactionService.ts` ~L1239–1700.
- **Refunds can be paid twice.**
  - `processRefund` validates against the transaction object passed in from the UI, not a fresh read.
  - It writes with `addDoc` outside any transaction.
  - It ignores `cancellationRefund.amount`.
  - Two concurrent refunds, or a refund after a cancellation, both pass.
- **Too many overlapping status fields:** `status`, `orderStatus`, `paymentStatus`, `deliveryStatus`, `cancellationRefund.status`, plus a `refunds` collection *and* a `refunds[]` array. The 6 one-off fix scripts in `scripts/` and the `admin/fix-*` routes show these fields have already drifted apart in real data.
- **Multi-step workflows are not atomic.** Restock, then update the transaction, then mirror to `onlineOrders`, then notify: each step is a separate write, and some failures are swallowed.
- **Audit trail is weak.**
  - `approvedBy`, `cancelledBy` and `refundedBy` are strings supplied by the client, often defaulting to `"System"`.
  - `deleteTransaction` hard-deletes financial records.
  - There is no append-only audit log.
- **Money uses floating-point math.**
  - Nothing is rounded to currency units, and MMK amounts are shown with `toFixed(2)`.
  - Divide-by-zero is possible when `currencyRate` is 0 (`settingsService.convertPrice`) and when the total is 0 (`PaymentClearanceModal` derives the exchange rate as `sellingTotal/total`).
  - The tax rate is reverse-engineered as `tax/(subtotal-discount)`.
- **Tax is never refunded** (`processRefund`). Expect the committee to question this. Under typical VAT rules a refund reverses the tax, so check local requirements.
- **The TXN counter silently falls back** to `TXN-<timestamp>-<random>` on error. The ID is allocated before the sale is confirmed, so cancelled previews leave gaps in receipt numbers.
- **Every request reads the whole collection.** Storefront `new-items`, `productSearch` (web search, AI chat and Telegram) and `top-selling` read all of `stocks` or `transactions` each time. POS `getTransactions(limit)` downloads everything and then calls `.slice()`.
- **Webhook edge cases.**
  - A stock conflict returns 409, so MMPay retries indefinitely and the order flips between `paid` and `stock_conflict`.
  - The check that a transaction already exists is a get-then-set, so duplicate callbacks can double-award points.
  - Points are based on `subtotal` here but on `total` in COD orders.
- **Upload validation is weak.** It only checks the MIME type the client claims, which allows SVG and HTML (a stored XSS risk on the public R2 domain). The client also chooses the `folder` prefix.
- **Little input validation.** Zod is installed but used only for the login form. Raw `error.message` is returned to clients.
- **AI chat is open to abuse.**
  - Anonymous, with no rate limit, up to 4 Groq calls per request, and the client can inject `role: "system"`.
  - The Telegram AI hardcodes a model that the web route's own comment says returns 404.

## 3. Workflows that are wrong

1. **POS takes stock when an item is added to the cart, not when it is paid.**
   - The reservation exists only in browser memory with no expiry. A closed tab or abandoned cart means that stock is gone for good.
   - On any error other than insufficient stock, `reduceInventoryStock` returns `true` anyway (`owner/home/page.tsx` ~L328), so the item stays in the cart without being deducted.
2. **Receipt printing records the sale.**
   - `handlePrintReceipt` awaits `handleConfirmPayment()` but never checks its result, then prints after `setTimeout(250)`. A receipt can print for a sale that was never saved.
   - The popup depends on the browser allowing popups.
   - The footer message is injected without HTML escaping.
3. **COD orders award loyalty points and consume coupons when the order is placed**, using the client's total. A customer can place an inflated order, collect the points, then cancel. Points should be awarded only on delivery or completion and reversed on cancel or refund.
4. **QR payment lifecycle.**
   - The 180-second expiry is enforced only in the browser.
   - Clearing the cart and releasing the coupon only happen if the tab stays open.
   - `/api/stock/release-expired` exists, but no cron job calls it, so abandoned QR stock stays locked until someone else checks out.
   - Every unauthenticated `create-order` call reserves real stock, so a script could lock the whole catalogue.
5. **Customer notifications depend on the POS browser.** The POS page calls `customer-event`, which forwards to the storefront. There is no Firestore trigger or outbox. If the tab closes or the call fails, the customer is never told and nothing retries.
6. **Telegram cancel does nothing.** The `confirm_cancel_*` button has no handler. `canCancelOrder` checks statuses that online orders never carry, and checks `"paid"` while MMPay writes `"SUCCESS"`.
7. **Branch identity is inconsistent.**
   - Branches are matched by name in some places and by id in others, so renaming a shop breaks filtering.
   - The settings page writes `localStorage` directly instead of going through the context.
   - `setCurrentBranch(name, true)` silently changes the default branch for every user.
8. **Online and in-store prices can differ.**
   - The storefront promotion formula (`lib/onlinePromotion.ts`) evaluates end dates in the *browser's* time zone.
   - The POS has its own discount logic.
   - The bot uses a hardcoded `ACTIVE_PROMOTIONS` list, so it can advertise deals that checkout won't apply.
9. **Stock can be deducted from the wrong variant.** `resolveVariantIndex` falls back to "variantId as array index", then "first colour match", then "size only".
10. **The documentation claims features the code doesn't have.** `PROJECT_OVERVIEW.md` lists:
    - "Server-side permission validation on all endpoints"
    - "Rate limiting"
    - "Zod runtime validation"
    - "httpOnly cookies"
    - "Offline mode ready"
    - "Real-time synchronized"

    Its schema also says `products` while the code uses `stocks`. A committee member who opens the code will notice.

## 4. Realtime: what is live and what is not

### POS
| Screen | Today | Problem |
|---|---|---|
| **Sell screen stock** (`owner/home`) | One-time `getDocs` plus a `sessionStorage` cache | Sales at other tills or online don't appear until a reload. `InventoryRealtimeService` is imported but never used. |
| Transactions list | One-time fetch of the **entire** collection | Manual refresh, and it reloads everything when the branch changes. |
| Dashboard | One-time `Promise.all` of all transactions, stocks, customers and expenses | Not live, and the cost grows with history. |
| Stocks / Customers pages | One-time `fetch` | Not live. |
| Sidebar badges, TopNavBar bell | `onSnapshot` on **all** transactions and notifications | **Listeners leak:** `unsubscribe` is returned from an async function, so the effect never cleans up. The sidebar mounts twice, and every navigation adds more full-collection listeners. |
| Pending refunds / refund pages | `onSnapshot` on the entire collection with an async callback and N+1 `getDoc` calls | Expensive. Overlapping snapshots can overwrite newer state. |
| Settings, cart, categories, online orders | `onSnapshot` with cleanup | ✅ Good. |

### Storefront
| Screen | Today | Problem |
|---|---|---|
| Catalogue / product page | `onSnapshot` on **all** `stocks` | Live, but every visitor downloads the whole catalogue, probably twice on first load. No error callback. |
| **Cart line prices** | Copied when the item is added | If the POS changes a price, sells out a size or deletes the product, the cart still shows the old values until checkout fails. |
| Settings (rate, tax) | Polled every 5 seconds with `gcTime: 0` | Wasteful; use `onSnapshot`. |
| Hero / new items | 5-minute stale cache | Lags behind. |
| Membership points | Fetched once | Points earned at the POS don't appear until a reload. |
| Notifications page | `getDocs` once | Not live. |
| Purchases (order status) | `onSnapshot` | ✅ Good. |

### Realtime fixes
- **POS sell screen:** use a branch-scoped `onSnapshot` (`where("shop","==",shopId)`) and drop the `sessionStorage` cache. Enable `persistentLocalCache` for offline tolerance.
- **Sidebar and TopNavBar:** move them into `app/owner/layout.tsx` so they mount once. Make the effect synchronous and return a cleanup. Replace the full scans with `where(...)` queries or a counters document maintained on the server.
- **Transactions and dashboard:** filter on the server (date, branch), paginate with `limit` + `startAfter`, and use `getAggregateFromServer` or daily summary documents for the dashboard.
- **Storefront cart:** subscribe to the cart's own product documents. Show "price changed", "only N left" or "unavailable", and block checkout until the customer resolves it.
- **Membership:** subscribe with `onSnapshot(customers/{uid})`.
- **Settings:** replace polling with `onSnapshot`.
- **Notifications:** use a Cloud Function (`onDocumentUpdated`) or a `notificationOutbox` collection drained by a cron job, with idempotency keys.
- **Cron:** schedule `/api/stock/release-expired` with Vercel Cron or Cloud Scheduler.

## 5. Frontend architecture

- **God components.** Line counts:

  | File | Lines |
  |---|---|
  | Web `account/purchases` | 4046 |
  | POS `sales/transactions` | 3530 |
  | POS `sales/reports` | 2895 |
  | `online-orders` | 2315 |
  | `customers` | 2236 |
  | `ShoppingCartModal` | 2187 |
  | `dashboard` | 2033 |
  | `PaymentClearanceModal` | 1853 |

  Firestore calls, business rules and JSX are mixed together, sometimes inside `onClick` handlers.
- **Duplicated business logic.**
  - "Is this a paid order?" is defined differently in the Sidebar and in the pending-refunds page, so the badge count and the list disagree.
  - Promotion math is repeated in 5 places on the storefront.
  - `new-stock` and `edit/[id]` are near-copies.
  - Currency formatting is reimplemented locally ("Ks" vs "MMK").
- **No data layer in the POS.** There is no React Query or SWR. Shops alone are fetched separately by 6 components on every navigation.
- **Storefront is fully client-rendered.** Every page is `"use client"` and the root layout sets `force-dynamic`. Product pages have no `generateMetadata`, Open Graph tags, sitemap or robots file, so SEO is effectively zero.
- **No offline support.** `sw.js` is a kill-switch and Firestore persistence is off. The POS cannot complete a sale if the internet drops, yet `manifest.json` suggests a PWA.
- **Type and log hygiene.** About 113 `any` in the POS and about 88 on the web. 135 + 105 `console.log` calls, some of which dump customer and transaction PII. Leftover `firebase-debug.log` and `build-log.txt` are committed. Dead code such as `page-optimized.tsx` and `api/new-items.ts` remains.

## 6. UI / UX design

### POS
- **No barcode-scanner workflow.** A clothing POS needs an always-focused scan field with Enter-to-add. Today the only search is by group name, and the Barcode menu is commented out.
- **About 30 native `alert()`/`confirm()`/`prompt()` calls** (refund rejection reasons, barcode entry, deletes). They block the UI, can't be translated and behave poorly on tablets, even though `react-hot-toast` and custom modals already exist.
- **Tablet layout.** The sidebar is hidden below `lg`, so tablets in portrait (the usual POS device) get only the hamburger overlay. Touch target sizes have not been audited.
- **Inconsistent visual system.**
  - Gradients run in both directions (rose→pink and pink→rose).
  - Pink, rose, purple, blue and green are mixed.
  - The theme colour is blue `#3b82f6` against a pink brand.
  - The shared `Button` component is used in only 13 files, against 382 raw `<button>` elements.
- **Weak loading and error states.** Most screens show only a spinner. The error recovery is `window.location.reload()`, and many errors go only to the console.
- **Accessibility.**
  - `maximumScale: 1` blocks pinch-zoom.
  - `lang="en"` is fixed even though a language switcher exists.
  - Only 11 of 137 `<label>` elements are linked to their inputs.
  - Full WCAG validation needs manual testing with assistive technologies.

### Storefront
- **Checkout has no delivery-fee line**, not even "Free". The total shown is the cart total plus tax only.
- **The cart shows stale prices and stock**, and "Clear Cart" empties it in one tap with no confirmation.
- **Developer text is shown to customers.** The MMPay sandbox-limit message says "Contact MyanMyanPay support…", and the test-payment button path ships in production.
- **i18n covers only 8 files.** Cart, product page, purchases, membership, auth and the chatbot are English only. Myanmar users see a flash of English on load.
- **Currency formatting is inconsistent.** The cart hardcodes `฿ x.toFixed(2)` / `Ks`, while other pages use `formatPrice`.
- **Images.** Fallbacks come from the third-party `via.placeholder.com`. 18 raw `<img>` tags are used where `next/image` would fit.
- **ChatBot.**
  - It has no `role="dialog"`, no Escape handler and no focus trap.
  - On phones the floating button can cover the sticky checkout buttons.
- **Contrast and loading.**
  - `text-gray-400` on white is low contrast.
  - Prices drawn as gradient text disappear in forced-colours mode.
  - The hero returns `null` while loading, which shifts the layout.
- **Unbacked marketing claims.** "Free Returns 7 Days" and "100% Authentic" are hardcoded but not supported by any workflow.

## 7. Engineering process

- **Zero automated tests** in either app: no Jest, Vitest or Playwright, and no `*.test.*` files. The money math (`stockMath`, discounts, refunds, `mmpayCallback`) is untested even though some modules were written to be testable.
- **No CI or rules emulator tests.** The `eslint-config-next` version (15.5) doesn't match Next 16. `"lint": "eslint"` has no target.
- **Dependencies use caret ranges** rather than pinned versions.

## 8. What is done well (acknowledge these in the defense)

- **Overselling is prevented.** Stock decrements run inside `runTransaction` (POS `StockService.adjustStock`, web `createOrderWithStockReservation` / `createCodOrderWithStock`).
- **Restocking is idempotent.** The `stockReturnLedger` and the `stockDeductedAt` / `stockRestoredAt` guards stop refund, cancel and release from restocking the same units twice.
- **Payments are partly protected.** MMPay callbacks are signature-verified, late EXPIRED callbacks after SUCCESS are ignored, and the frontend never marks an order paid by itself (apart from the test-complete route).
- **Telegram account linking is solid.** Tokens are random, expire after 15 minutes, are single-use and are claimed inside a transaction.
- **Delivery area is enforced on the server.**
- **Secrets are handled correctly.** `.env*` is git-ignored and no keys appear in tracked source.
- **Several live updates work well:** the settings, cart and online-orders listeners (including retry and resubscribe).

## 10. Recommended fix order

**Phase 1: Security (highest impact, smallest effort)**
- Add `authoriseRole` / `getUidFromAuthHeader` to every API route and take the uid from the verified token, never from the body.
- Delete the `admin/*`, `test/*` and `fix-*` routes. Gate `test-complete` behind `NODE_ENV !== "production"` plus an owner token.
- Make the Telegram webhook fail closed and compare the secret with `timingSafeEqual`.
- Switch POS server routes to `adminDb`.
- Test the rules in the emulator, add field allow-lists (customers may edit profile and cart fields only), then deploy.
- Require auth on R2 uploads, check file contents against a jpeg/png/webp allowlist, and generate object keys on the server.

**Phase 2: Money correctness**
- Calculate prices on the server for `create-order`, `create-cod` and a POS checkout endpoint. The client sends only `{productId, variantId, size, qty, couponId}`.
- Make the webhook reject callbacks whose amount doesn't match.
- Build one `orderStateMachine` module with an allowed-transitions table, checked inside `runTransaction` on a fresh read. Keep payment, fulfilment and refund status as separate fields, and keep refunds in a single store.
- Award loyalty points only on completion and reverse them on cancel or refund.
- Store money as integer minor units with one rounding policy.
- Replace hard deletes with soft delete, and add an append-only `auditLog` whose actor comes from the verified uid.

**Phase 3: Realtime and workflows**
- Apply the §4 fixes: branch-scoped POS stock listener, layout-level Sidebar and TopNavBar, server-side filters and pagination, aggregates for the dashboard, live cart revalidation.
- Add a notification outbox or Cloud Function, plus a cron job for reservation release.
- Record the sale first, then print from a hidden iframe on `load`.
- Identify branches by `shopId` everywhere.

**Phase 4: UX**
- Barcode scan input and keyboard shortcuts on the POS.
- A shared `ConfirmDialog` / `PromptDialog` to replace native dialogs.
- One `formatPrice` function used everywhere.
- A delivery-fee line at checkout.
- Complete i18n coverage.
- Tablet layout pass.
- Accessibility fixes (zoom, labels, ChatBot dialog semantics, contrast).
- Server-rendered product pages with metadata and a sitemap.

**Phase 5: Tests (also strengthens the defense)**
- Vitest for pricing, `stockMath`, `mmpayCallback` and cart merge.
- `@firebase/rules-unit-testing` for the rules.
- Playwright for the cash sale → refund flow and the COD checkout → cancel flow.
